# M4-L4 – Compulsory elective: Formal verification, type theory and proof assistants {#L4}

**Course area:** M4 – Choice of study: AI, computer science and specialised fields

**Prior knowledge:** [M1-L1](M1-L1.md) (logic and induction), [M2-L13](M2-L13.md) (formal languages and computability), [M1-L3 – School Mathematics (German-language course)](https://monowlith-com.github.io/learning-courses/index.html?course=school_mathematics&module=M1&lesson=L3&syslang=de&doclang=de&theme=light) (equivalence transformations)

**Context:** Computer science specialisation, from advanced Bachelor’s to Master’s level.

## What is this about? {#S1}

A program can behave correctly in thousands of tests and still contain an error affecting a case that has not yet been tested. **Formal verification** therefore attempts to prove certain properties of a program mathematically. The aim is not to prove every conceivable property of software: first we must specify precisely what should hold, under which assumptions and for which program or machine model. Type theory helps distinguish meaningful propositions and program expressions. Finally, proof assistants can check whether the stated proof steps actually follow from the rules.

## Basic idea: From a test case to a general contract {#S2}

A test might check the input $x=4$, for example. A mathematical program contract, by contrast, asserts: ‘For **every** integer that is at least zero, this program returns a value that is at least one.’ The contract is stronger when its conditions are satisfied exactly. However, it also depends on the program under investigation and its semantics being modelled correctly.

The most important distinction is: **test** = selected concrete execution; **proof** = deduction for all cases covered by the assumptions; **runtime monitoring** = checking during execution. These three approaches complement one another.

## Preconditions and postconditions: A complete proof {#S4}

We consider a **mathematical** program with an integer variable $x$ and exact arithmetic:

Formula, sketch or calculation scheme · Original notation

    C:  x := x + 1
    P:  x ≥ 0
    Q:  x ≥ 1

    { x ≥ 0 }  x := x + 1  { x ≥ 1 }

Read aloud: ‘If the input value x is at least zero, then x is at least one after the assignment.’ Why? Let the value before execution be $x_{\mathrm{alt}}$. Then after the assignment, $x_{\mathrm{new}}=x_{\mathrm{alt}}+1$ holds. From $x_{\mathrm{alt}}\ge 0$ it follows that $x_{\mathrm{new}}\ge 1$. This is not an enumeration of test cases, but a general calculation.

An example: for $x_{\mathrm{alt}}=4$, the result is $x_{\mathrm{new}}=5$. A boundary case: for $x_{\mathrm{alt}}=0$, the result is $x_{\mathrm{new}}=1$. Both are covered by the proof, as are all other non-negative integers.

**Important assumption:** With bounded machine integers, $x+1$ may overflow. For a signed 32-bit integer with a range from $-2147483648$ to $2147483647$, we must take possible overflow semantics into account and, for example, add $0 \le  x \le  2147483646$ as an input bound. Only then does the mathematical postcondition remain within this range. Whether overflow is undefined in the actual language, raises an exception or is handled according to fixed rules depends on its semantics. A proof about unbounded mathematical integers does not automatically apply to arbitrary machine code.

In Hoare logic, the triple conventionally denotes **partial correctness**: if execution terminates, the postcondition holds. For **total correctness**, termination must also be guaranteed. The particular assignment terminates in our simplified model.

## Weakest precondition: Reasoning backwards {#S5}

We want to execute the instruction $x := x + 2$ and guarantee the condition $x \ge  5$ afterwards. What minimum value must hold **beforehand**?

Formula, sketch or calculation scheme · Original notation

    Q: x ≥ 5
    C: x := x + 2

    wp(C,Q): x + 2 ≥ 5
             x ≥ 3.

Read aloud: ‘We substitute the right-hand side of the assignment into the desired postcondition; this requires x plus two to be at least five. So x being at least three is sufficient.’ For a simple assignment, the following holds in general:

$$
\operatorname{wp}(x\mathrel{:=}E,Q)=Q[x\leftarrow E]\text{.}
$$

$E$ is an expression, and $Q$ is a proposition about the state after execution. The notation $Q[x\leftarrow E]$ on the right means **substitute E for the free occurrences of x in Q**; when quantifiers and bound variables are involved, substitution must be carried out correctly, without accidental variable capture. ‘Weak’ means that the input requirement is no stronger than necessary. With side effects, exceptions, randomness and more complex programs, such simple substitution rules are not automatically sufficient.

## Loop invariants and termination {#S6}

A common error occurs not in a single instruction, but in a loop. We want to add the numbers from $1$ to $n$; let $n$ be a fixed natural number.

Formula, sketch or calculation scheme · Original notation

    i := 0
    sum := 0
    while i < n:
        i := i + 1
        sum := sum + i

The appropriate **loop invariant** is:

$$
I:\quad0\leq i\leq n\quad\text{and}\quad\mathrm{sum}=\frac{i(i+1)}2\text{.}
$$

Read aloud: ‘At every loop state reached, i is between zero and n. The sum equals i times i plus one, divided by two.’ We check the three crucial steps:

1.  **Initialisation:** $i=0$, $\mathrm{sum}=0$, hence $\frac{i(i+1)}2=0$; the invariant holds.
2.  **Preservation:** Suppose the invariant is true before another iteration and $i<n$. After the increment, $i_{\mathrm{new}}=i+1$. The new sum is $\frac{i(i+1)}2+(i+1)=\frac{(i+1)(i+2)}2$, exactly the required formula for $i_{\mathrm{new}}$.
3.  **Exit:** When the loop stops, $i\ge n$ holds. Together with $i\le n$, this implies $i=n$. Hence $\mathrm{sum}=\frac{n(n+1)}2$.

To establish termination, the non-negative integer $n-i$ serves as a **loop variant**: it decreases by one in each iteration. An invariant shows a preserved property; a variant provides the termination argument here.

**Numerical example:** $n=4$ produces $\mathrm{sum}=1+2+3+4=10$. The formula gives $\frac{4\cdot5}2=10$. The calculation merely illustrates the result that has already been established in general.

## Type theory: Bringing programs and propositions together {#S7}

A **type** describes the kind of object expected: a natural number, a list of natural numbers or a function that computes one number from another. In logic, from the **Curry–Howard perspective**, a type often corresponds to a proposition and a value of that type to a proof of the proposition.

An elementary example is the proposition ‘From A and the implication from A to B, B follows’:

Formula, sketch or calculation scheme · Original notation

    A    : Prop           a proposition A
    B    : Prop           a proposition B
    hA   : A              a proof of A
    hAB  : A → B          a mapping from proofs of A to proofs of B
    hAB hA : B            a proof of B

Read aloud: ‘Apply the function that turns a proof of A into a proof of B to the existing proof of A.’ This perspective is useful for treating proofs as checkable objects. It does not automatically make every arbitrary program a proof of safety.

**Dependent types** can also incorporate values into the description of a type. A vector ‘exactly five elements long’ may have a different type from a vector ‘exactly four elements long’. Certain dimensional errors can thus be ruled out during type checking. However, this does not automatically protect against incorrect measurement data, insecure access rights or side effects.

## A tiny Lean proof {#S8}

The following **Lean 4 example** demonstrates modus ponens. It uses only propositional logic and the built-in proof facilities. For reference: [Theorem Proving in Lean 4, chapter on propositions and proofs](https://lean-lang.org/theorem_proving_in_lean4/Propositions-and-Proofs/).

    example (A B : Prop) (hA : A) (hAB : A → B) : B := by
      exact hAB hA

Line by line: `A B : Prop` introduces two propositions. `hA : A` means that A is assumed to have been proved. `hAB : A → B` is a proof of the implication. To the right of the colon after the last parenthesis is the goal `B`. The instruction `exact hAB hA` presents the checker with precisely the proof constructed from the two assumptions.

A proof assistant checks such proof objects against a small logical kernel. A successful check makes a strong statement about the **formalised goal in the chosen system**, but does not establish that our informal problem formulation perfectly captures the real requirement. ## Model checking: Examining finitely many states systematically {#S9}

In **model checking**, the possible states and transitions of a modelled system are systematically examined. Example: an automaton has the states `Waiting`, `Working` and `Error`. A condition might be: ‘In no reachable state is motor power active while the protective cover is open.’ Rather than looking at individual test runs, the method checks the reachable transitions of the model.

In the branching-time logic **CTL**, $\mathrm{AG} p$ means: ‘On all possible paths, the proposition p holds in every state.’ By contrast, $\mathrm{EF} q$ means: ‘There is at least one path on which q eventually holds.’ Here, $A$ is the universal path quantifier, $E$ the existential path quantifier, $G$ indicates that a proposition holds globally and $F$ that it eventually holds.

The two statements are fundamentally different. ‘A safe state is eventually reachable’ ($\mathrm{EF} \mathrm{safe}$) does not imply that **all** executions remain safe at all times ($\mathrm{AG} \mathrm{safe}$). With a large or infinite state space, there is a risk of **state explosion**; abstraction and symbolic methods are then necessary.

### Countercheck: The existence of a safe execution does not imply general safety {#abschnitt-10}

We make the CTL statements checkable using a minimal illustrative transition system: there is an **initial state W** (Waiting, safe) and an **error state F** (unsafe). The transitions are $W\to W$, $W\to F$ and $F\to F$. The proposition `safe` holds only in W, and the proposition `error` only in F. Each state has at least one successor, so infinite paths are also defined in the model.

Formula, sketch or calculation scheme · Original notation

    Start: W.
    Path 1: W → W → W → …        always safe.
    Path 2: W → F → F → …        unsafe from F onwards.

    EF safe    is true in W: W itself is already safe.
    AG safe    is false in W: Path 2 reaches F.
    EF error   is true in W: Path 2 reaches F.
    AG ¬error  is false in W: Path 2 reaches F.

Read aloud: ‘One possible safe execution does not prove that all executions are safe.’ Here, $\neg$ means ‘not’. The trace $W\to F$ is a **concrete counterexample** to the asserted universal path property $\mathrm{AG} \mathrm{safe}$ – within the model. Whether a real automaton can reach the same state must be examined separately.

### Countercheck: A proof is tied to its number model {#abschnitt-11}

For the contract $\{x\ge 0\} x:=x+1 \{x\ge 1\}$ from Section 1, the precondition is sufficient for a mathematically unbounded integer. For the finite signed 32-bit representation, by contrast, the stronger condition $0 \le  x \le  2147483646$ is necessary if we want to guarantee that the addition remains within the representable range **without overflow**. With the boundary value $x=2147483646$, we obtain $2147483647$, an admissible value. For $x=2147483647$, $x+1$ falls outside the range. This demonstrates the limitation of the original model specification without assuming any particular programming language or runtime.

## What is it useful for? {#S10}

Formal verification is particularly relevant to the safety properties of control systems, access logic, cryptographic protocols, database transactions and critical software components. Type checkers prevent certain classes of errors at an early stage. Model checking can produce counterexamples in the form of sequences of states when a specified property is violated in the model. Proof assistants support detailed mathematical arguments, including foundations of AI and optimisation.

## Assumptions and limitations {#S11}

A mathematically correct model may fail to capture reality. Crucial factors include **the quality of the specification**, actual machine arithmetic, external libraries, timing behaviour, hardware, concurrency and trust in the compiler and runtime environment. Undecidability from M2-L13 explains why there cannot be a general algorithm that automatically guarantees a complete decision for every possible program and every non-trivial program property. Nevertheless, particular program properties can be proved.
